# 01 · 定位：为什么在 eino 与业务 agent 之间放一层 einox

> 三层栈：**eino（地基）→ einox（增强基座）→ 业务 agent（应用）**。

## 出发点：未来 agent 的形态不是通用聊天框

聊天框是聊天机器人时代的交互遗产。agent 的价值不在「能聊天」，而在嵌入领域系统后获得的三样东西：**数据**（业务真源与工具面）、**权限**（门禁与审批流）、**流程**（工作流与人机协作节奏）。一个只活在通用聊天框里的 agent，这三样都要靠外挂补丁；而 agent 作为业务系统的内置组件时，它们是原生结构——审批卡出现在业务自己的界面里，写入经过业务自己的门禁，会话归属于业务自己的用户。

所以 einox 的第一决策是形态：**做可装配的基座库，不做应用**。交互形态（终端 / Web / IM / 语音）与业务面归应用，基座只提供机制。这也决定了下面两个选型问题的答案。

## 各层是什么

| 层 | 角色 | 提供 | 不提供 |
|---|---|---|---|
| [cloudwego/eino](https://github.com/cloudwego/eino) | LLM 应用框架（地基） | 模型组件抽象、消息 schema、编排原语（compose）、agent 内核（adk）、官方组件生态（eino-ext） | agent 运行时关切：会话生命周期、审批挂起、沙箱执行、网络容错、上下文整形 |
| **einox** | 通用 agent 基座（本仓） | 循环引擎、会话域、HITL 审批、harness（上下文整形/摘要/子代理隔离/动态工具装载）、沙箱、网络容错、通用工具族、skill 机制、检查点 | 业务内容：业务工具、提示词内容、审批名单、UI、数据门禁 |
| 业务 agent | 应用（不在本仓） | 按上述机制装配出自己的 agent 系统 | ——机制由基座承担 |

## 为什么不直接 eino → 业务 agent

eino 解决的是「**怎么调模型、怎么组装组件**」；一个能上生产的 agent 系统还需要一整层「**怎么跑起来**」的运行时关切，这些不在 eino 的面里：

1. **会话生命周期**——会话归属、快照、续聊、排队消息、运行中改向（steering）、TTL 清理；
2. **HITL 审批**——写操作挂起等人批准、恢复续流、参数级强制审批（任何模式不豁免）、fail-closed；
3. **执行安全**——命令沙箱（Landlock/seccomp/restricted token/Seatbelt）、网络出口治理、代码仓 worktree 挂载与「不 push」边界；
4. **网络容错**——流式空闲哨兵、错误分类（致命停机/可重试）、有界重连——没有它们，一条静默死链就让会话永远 running；
5. **harness**——出站上下文经济（超长工具结果外置换指针、历史超窗清除）、长会话摘要、子代理隔离与编排、动态工具装载——上下文管理是 agent 的第一生产资料；
6. **通用工具族**——apply_patch / 文件面 / 命令执行 / 网页提取……每个 agent 系统都要，不该每家重写。

直接从 eino 写业务，上面六条会散落在每个业务系统里各造一遍，且互相不可复用。einox 把它们收敛为**机制**，一次实现、处处装配。

## 为什么不直接用 codex / deepseek-harness

[openai/codex](https://github.com/openai/codex) 与 [deepseek-harness](https://github.com/deepseek-ai/deepseek-harness) 都是优秀的 agent 实现，einox 也确实站在它们肩上——apply_patch 格式与匹配算法、沙箱策略、harness 概念均有移植/借鉴（清单见 [NOTICE](../NOTICE.md)）。不直接用，是因为**它们是应用，不是库**：

- **形态锁死**：codex 是终端编码助手，dsh 是 TypeScript 生态的 harness——运行时形态、配置体系、会话模型、交互面都是既定产品决策，嵌进业务系统等于带着整套产品外壳。
- **进程边界**：业务系统是 Go 服务，引入 Rust/TS 运行时只有两条路：子进程旁挂，没有进程内契约——审批卡进不了业务自己的 UI，会话与权限无法共域；fork 改造，永久分叉负担，每次升级都是冲突。
- **关注点不同**：它们为「编码代理」优化（终端、开发者用户）；业务 agent 的一等公民是领域数据门禁、多租户会话、审批矩阵——这些在应用型项目里不是设计中心。

库形态让业务系统 import 即得全部机制，且按需裁剪（见 [03](03-assembly.md)）。

## 为什么选 eino、选 Go

**Go**：服务端并发模型（goroutine 天然承载多会话、多 agent、多子代理并发）、静态类型的进程内契约，以及下述单一二进制形态。

**eino**：Go 生态里最完整的 LLM 应用框架——消息 schema、模型组件抽象（anthropic / openai 协议组件）、compose 编排原语、adk agent 内核与模型重试协议、eino-ext 组件生态（MCP、搜索等）——全部以库形态提供，不改源码直接消费、随上游升级。模型面的脏活（协议适配、流式、重试）eino 已经做完，einox 不重造；这也是「先挖尽 eino 既有能力，确无才自研」实现序铁律的由来。

**单一二进制**：某些场景下这是决定性便利——内网与离线部署，一个静态编译的 Go 二进制（前端资源可 embed 在内）把服务与 agent 能力全部内置：部署 = 拷一个文件，升级 = 换一个文件，不需要 Node 运行时、Python 环境或旁挂服务。对内网中小团队，运维面的简洁是硬收益。

## 设计原则

- **机制归基座，内容归业务**：审批的挂起/续流是机制（基座），审批名单是内容（业务）；skill 的发现与注入是机制（基座），skill 本身是内容（业务仓）。
- **应用对基座只装配、不修改**：全部能力经 `engine.Options` 注入与启停，基座源码不改一行。
- **业务 0 import eino**：eino 依赖唯一所在地是本仓；业务只见 `contract` 契约面（零 eino 类型）——换地基只动基座内部。
- **能力面不裁剪，装配面自由裁剪**：多代理编排、动态工作流、harness 层等是基座必备机制，不因某个应用暂不用而删除；应用不装配即不生效。
- **实现序**：先挖尽 eino 既有能力（中间件/原语/预置拓扑），确无才自研并在设计文档记「eino 无 X」依据。

## 术语

多代理技术双轴命名：**多代理编排**（现场编排，orchestrator-workers——父 agent 逐轮决定派谁）与**动态工作流**（agent 把编排写成脚本制品运行）是两种机制；**子代理**（spawn）是唯一原语，同步调用与后台派生（`background:true`，即回 agentId、完成通知回传）是它的两种调用语义；并行/顺序/条件只是拓扑，不构成机制名。
