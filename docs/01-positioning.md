# 01 · 定位：为什么在 eino 与业务 agent 之间放一层 einox

> 三层栈：**eino（地基）→ einox（通用 agent 基座，本仓）→ 业务 agent（应用）**。

## 出发点：每个系统各自智能化

业界的主流叙事是打造一个足够完善的 agent：由一个智能体对接并管理所有系统，其余一切为它让路——业务提供接口，生态提供插件，用户安装技能。einox 的判断与此相反：**需要各自智能化的是每一个系统，而不是用一个智能体去管理所有系统**——智能化是系统内生的能力，不是外挂在系统旁边的另一个系统。

分歧的根源在 agent 价值的真正来源。agent 的价值不在“能聊天”——聊天框是聊天机器人时代的交互遗产——而在嵌入领域系统后获得的三样东西：**数据**（业务真源与工具面）、**权限**（门禁与审批流）、**流程**（工作流与人机协作节奏）。只存在于通用聊天框里的 agent，这三样都要靠外挂补丁；而 agent 作为业务系统的内置组件时，它们是原生结构——审批卡出现在业务自己的界面里，写入经过业务自己的门禁，会话归属于业务自己的用户。

所以 einox 的第一项决策落在形态上：**做可装配的基座库，不做应用**。交互形态（终端 / Web / IM / 语音）与业务面归应用，基座只提供机制。后文依次展开：设计原则与技术选型（“设计原则”“为什么选 eino”）、三层职责切分与中间层的必要性（“各层是什么”“为什么不直接 eino → 业务 agent”）、库形态与其他四种交付形态的对比论证（“形态对比”），以及一份基座服务多套业务系统的适配结构（“场景适配”）。

## 设计原则

形态决策之下，五条原则贯穿全仓：

- **机制归基座，内容归业务**：审批的挂起/续流是机制（基座），审批名单是内容（业务）；skill 的发现与注入是机制（基座），skill 本身是内容（业务仓）。
- **应用对基座只装配、不修改**：全部能力经 `engine.Options` 注入与启停，基座源码不改一行。
- **业务 0 import eino**：eino 依赖唯一所在地是本仓；业务只见 `contract` 契约面（零 eino 类型）——更换地基只动基座内部。
- **能力面不裁剪，装配面自由裁剪**：多代理编排、动态工作流、harness 层等是基座必备机制，不因某个应用暂不用而删除；应用不装配即不生效。
- **实现序**：优先复用 eino 既有能力（中间件/原语/预置拓扑），确无对应能力才自研，并在设计文档中记录“eino 无 X”的依据。

## 为什么选 eino

选型服从上述原则，分三步：先选框架，再看交付，最后选定 eino。

**先选框架。**框架为基座承担共性底层：消息 schema、模型组件抽象、编排原语、agent 内核——这些不应自研，选型先看现有框架。当前主流的 agent 框架分属四种语言生态：

| 语言 | 生态与代表框架 | 交付形态 |
|---|---|---|
| **Python** | LangChain/LangGraph、OpenAI Agents SDK、AutoGen、CrewAI；模型厂商的第一方 SDK 大多 Python 优先 | 解释器 + 依赖环境（venv / pip），可复现的服务端部署通常需容器化 |
| **TypeScript** | Vercel AI SDK、LangChain.js、Mastra；前端与全栈生态成熟 | Node 运行时 + node_modules，离线交付需打包整套运行时 |
| **Rust** | codex CLI（Rust 实现）、Rig；性能取向，框架生态最年轻 | 编译型，静态单二进制 |
| **Go** | eino（CloudWeGo）、langchaingo（社区移植）；框架选择少而精 | 编译型，静态单二进制（交叉编译开箱即用） |

**再看交付。**einox 以库形态嵌入业务系统，内网与离线部署是常态，此时单一二进制是决定性便利：一个静态编译的二进制（前端资源可 embed 在内）把服务与 agent 能力全部内置，部署即拷贝一个文件，升级即替换一个文件，无需 Python 解释器、Node 运行时或旁挂服务；对内网中小团队，运维面的简洁是硬收益。语言由此收敛到编译型的 Go 与 Rust，两者之间取 Go：agent 的性能瓶颈在模型端点与网络 IO，不在宿主进程，Rust 的极致性能在此收益有限；Go 的 goroutine 并发模型天然承载多会话、多 agent、多子代理并发，静态类型给出进程内契约，库形态嵌入的宿主又天然是 Go 服务——同语言、同进程、同制品。

**最后选定 eino。**Go 生态中的框架选择本就不多，其中最完整的是 eino：消息 schema、模型组件抽象（anthropic / openai 协议组件）、compose 编排原语、adk agent 内核与模型重试协议、eino-ext 组件生态（MCP、搜索等），共性底层一项不缺；更关键的是，这些能力全部以库形态提供：不改源码即可消费、随上游升级。模型接入的底层工作（协议适配、流式、重试）eino 已经完成，einox 不重造，这也是“优先复用 eino、确无才自研”这条实现序的由来。

两者结合，选型落定：Go 的交付形态让基座以单二进制编入业务系统，eino 的库形态地基让基座不重造模型接入——einox 建在两者之上，只补 eino 能力面之外的 agent 运行时关切。

## 各层是什么

地基选定，三层栈的职责切分如下：

| 层 | 角色 | 提供 | 不提供 |
|---|---|---|---|
| [cloudwego/eino](https://github.com/cloudwego/eino) | LLM 应用框架（地基） | 模型组件抽象、消息 schema、编排原语（compose）、agent 内核（adk）、官方组件生态（eino-ext） | agent 运行时关切：会话生命周期、审批挂起、沙箱执行、网络容错、上下文整形 |
| **einox** | 通用 agent 基座（本仓） | 循环引擎、会话域、HITL 审批、harness（上下文整形/摘要/子代理隔离/动态工具装载）、沙箱、网络容错、通用工具族、skill 机制、检查点 | 业务内容：业务工具、提示词内容、审批名单、UI、数据门禁 |
| 业务 agent | 应用（不在本仓） | 按上述机制装配出自己的 agent 系统 | ——机制由基座承担 |

再从开发节奏看这条栈：einox 是对 eino 的**二次开发**，产物刻意止步于**半成品**；业务系统的组装根装配是**三次开发**，产物才是成品——各自的 agent。其他架构的二次开发通常以成品收尾，einox 把完成度边界划在“适配路径走通”——成品永远在业务侧诞生（判定见“形态对比”一章）。

## 为什么不直接 eino → 业务 agent

eino 解决的是“**怎么调模型、怎么组装组件**”；一个能上生产的 agent 系统还需要一整层“**怎么跑起来**”的运行时关切，它们不在 eino 的能力面里：

1. **会话生命周期**——会话归属、快照、续聊、排队消息、运行中改向（steering）、TTL 清理；
2. **HITL 审批**——写操作挂起等人批准、恢复续流、参数级强制审批（任何模式不豁免）、fail-closed；
3. **执行安全**——命令沙箱（Landlock/seccomp/restricted token/Seatbelt）、网络出口治理、代码仓 worktree 挂载与“不 push”边界；
4. **网络容错**——流式空闲哨兵、错误分类（致命停机/可重试）、有界重连——缺少它们，一条静默失效的连接就会让会话永远停留在 running 状态；
5. **harness**——出站上下文经济（超长工具结果外置换指针、历史超窗清除）、长会话摘要、子代理隔离与编排、动态工具装载——上下文管理是 agent 的第一生产资料；
6. **通用工具族**——apply_patch / 文件面 / 命令执行 / 网页提取……每个 agent 系统都需要，不应各自重写。

直接从 eino 写业务，上述六项会散落在每个业务系统里重复实现，且互相不可复用。einox 把它们收敛为**机制**，一次实现、处处装配。

## 形态对比：五种路线

前面回答的是“要不要在 eino 与业务之间放一层”；本章回答“这一层以什么形态交付”。五条路线的差别先在理念、后在成本。应用、平台插件、SDK、配置运行时四条路线无论交付什么，瞄准的都是**一个足够完善的 agent**——二次开发补齐功能、插件、配置、技能，得到最终形态的成品，思路仍是“一个产品满足所有需求”；对认可“由一个超级 agent 管理所有系统”的团队，这些正是与该理念相配的产品形态，照此选型并无不可。einox 的前提已在“出发点”一章立明：每个系统各自智能化；与这条理念相配的形态是 **agent 工厂**——基座自己不产出 agent，每个业务系统用它各自生产一个，成品在业务侧诞生。这是定义，不是缺陷。

理念各配各的形态；成本则要在同一场景下比较。einox 的目标场景是**把 agent 能力内置到业务系统中**——业务有自己的工具、技能与安全边界要求；交互通道未必有界面（电话语音、实时流媒体）；部署形态不定（个人独占与多租户共享皆有可能）。五条路线都能适配这一场景，差别在方法与成本；einox 自身的代价也如实列出——没有开箱即用，每个业务系统都要写组装根。

### 应用形态：业务提供 API，应用来调用

- **优点**：开箱即用；业务零重构——暴露 API（或执行其无界面 CLI）即获智能化。
- **缺点**：能力归应用。agent 对业务能做什么，等于 API 暴露面与应用工具层封装的乘积——业务自有的工具、技能与安全边界没有安放之处，只能做进应用。这是结构缺口而非能力缺口：应用与模型再强大，也替代不了业务原生的工具面与领域门禁；而把每个业务的需求都做进应用，应用必然随业务数膨胀——能力中心成为排期瓶颈、替所有业务承担安全责任；会话归应用的用户域，审批落在应用的界面。

### 平台插件形态：业务写成插件

- **优点**：业务侧有承载之处——平台用什么语言，插件就用什么语言，语言从来不是这条路线的障碍；个人助手场景的最优解：通用对话界面 + 技能市场，按需安装插件——既保住特定业务场景，本体又不膨胀。
- **缺点**：与应用形态同一个问题——对业务的支持方式。装满插件的平台殊途同归：插件开发到最后仍是一个应用支撑多种业务，膨胀只是转移进了插件生态，每接入一种业务就多一个插件；插件缝以下（会话归属、审批通道、多租户划分）皆为平台领地；部署重——本地 agent 之外还需维持在线插件库，离线场景只能以软件包导入插件、预配置后交付，agent 与业务仍是两套制品、两套界面，业务系统并未获得内生的 agent 能力。

### SDK 形态：进程外运行时 + 驱动客户端

- **优点**：无界面场景天然适配（本就无 UI 假设）；多租户即把运行时部署为共享服务；进程隔离。
- **缺点**：一切交互经由协议——自定义工具、审批回调、权限判定都是跨进程往返，类型契约止步于报文形状；会话与账号分属两个域，两侧要做映射与对账；双制品、双升级节奏，版本偏差需要管理。

### 配置驱动形态：业务写进配置与脚本

- **优点**：起步最快——修改配置即可运行。
- **缺点**：表达力止于配置语法——必须写代码的策略（审批矩阵、领域门禁、多租户）一旦超出配置的表达力，就退化为旁挂脚本，脱离类型系统与测试的保障；安全边界只有开关粒度、没有策略粒度；仍是独立运行时，交付两套。

### 装配形态：组装根在业务代码里（einox）

这一形态由四个事实界定：`contract/` 是唯一端口面（零 eino 类型——依赖倒置隔离地基，更换地基业务零感知）；全部能力经 `engine.Options` 组装根注入、构造期定型（运行面控制反转：引擎驱动循环、事件回调扇出），无容器、无运行时注册表；机制归基座并守安全不变量，策略经装配注入；`Options` 字段即全部装配缝——封闭枚举、编译期可见，新缝走基座演进，不经旁挂。

- **优点**：业务能力的载体是业务代码——工具、审批名单、提示词、边界策略是业务工程的一等代码，可测试（`llmtest` 零端点）、可 review、随业务系统同一制品交付；形态中立——无 UI 假设、事件传输无关（语音网关、流媒体管线即前端），部署形态（个人独占 = 单二进制 / 多租户 = 单进程按 Owner/SID 划域）是装配决策而非架构分叉；机制（审批包装、错误回喂、摘要、沙箱）由基座在装配链统一施加，业务不重写机制。
- **缺点**：没有开箱即用，每个业务系统要写组装根；扩展缝封闭于 `Options` 枚举——三方插件、运行时增删不在设计目标内。

### 判定：拆“能力 | 成品”，不只是“能力 | 内容”

三层栈的核心是把**能力补全**与**最终成品**拆开，让能力补全一次完成、N 处复用。拆分成立要求能力工件满足三个条件：**可复用**（N 处消费不分叉）、**业务差异装配得出**（不必改能力层源码）、**形态中立**（不携带产品形态，否则 N 个成品长成同款）。三个条件对各路线都不存在能不能做到的问题——应用形态靠 fork 也拆得出引擎——真正的差别在方式，以及两项要按工作量与时间结算的成本：**对齐成本**（能力层如何持续跟上上游）与**传导成本**（变更到达业务侧后，业务跟进的工作量是否可预期）。“可以做到”磨平不了这两项成本。

差别源于能力工件的形状：**可运行之物必带形态**——应用带界面、平台带宿主与生态、SDK 带协议与进程边界、配置带 schema。形态在能力侧，成品就继承它；要改形态就得动能力层，而动能力层只有推上游或 fork 两条路，付出的都是排期与人力。库的能力工件是**不可运行的代码**，形态由装配赋予——业务差异不动能力层即可表达，对齐收敛为依赖升级，破坏点编译期可枚举，变更以拉取方式到达（不升版本，变更不进入业务代码）。一句话：**其余四条路线拆的是“能力 | 内容”，装配路线拆的是“能力 | 成品”——成品包含形态与交付，唯有库形态能完成这一拆分**。

两个退化情形同理：fork 是以修改代替装配，能力补全实际被做了 N 次；平台的机制包当库用可行，但其零件为平台而非嵌入塑形，也不被对方的设计所守护——**可行不等于被设计支持，可行不等于成本可预期**。

判定同时是对基座自身的纪律：契约面零形态与 nil 纪律守护复用面——每混进一个形态假设，就塌陷一块复用面；装配点的表达力与契约的稳定守护业务的跟进成本——业务差异若只能改基座源码表达，分离即告失败，而 `contract` 面的破坏性变更就是业务工作量的上界：窄、少动、编译期可检。

### 总表

| 形态 | 业务能力的载体 | 能力复用方式 | 变更到达业务侧 | 交付 |
|---|---|---|---|---|
| 应用 | API 面 | fork 源码拆引擎 | 人工合并，分叉随拖延期加深 | 应用方的一个 agent |
| 平台插件 | 插件 | 平台工件 + 插件缝 | 推送：破坏性版本 = 插件返工，节奏由平台定 | 两套（平台 + 插件） |
| SDK | 协议报文 | 运行时工件 + 协议面 | 跟运行时节奏，协议破坏运行期才暴露 | 两套（业务 + 运行时） |
| 配置驱动 | 配置 / 脚本 | 运行时工件 + 配置方言 | 静默漂移，排障时间不可预期 | 两套 |
| **装配（einox）** | **业务代码** | **库工件 + 类型化装配点** | **拉取：升依赖才进入，破坏点编译期可枚举** | **一套（agent 编在业务系统里）** |

对业务而言，表中最后一行就是全部代价与收益：以一个组装根，换取能力复用、变更可控与单制品交付——import 即得全部机制、按需裁剪（见 [03](03-assembly.md)）；对第三方实现的移植与借鉴（apply_patch 格式、沙箱策略等）在 [NOTICE](../NOTICE.md) 逐项署名。

## 场景适配：一份基座，多套业务系统

单系统嵌入时，库形态的价值是“不带产品外壳”；到组织级场景，这一价值才完整显形——“agent 工厂”名副其实的场景正在于此：**一个团队为多套业务系统提供 agent 能力**，CRM、工单、数据平台、内部工具，每套都有自己的数据域、权限模型、审批流与交互形态。einox 为这一场景提供的适配结构有四条：

**同一份基座，N 个组装根。** 每个业务系统一个组装根——`engine.Options` 即该系统的 agent 定义。系统间差异是应用代码差异：可 review、可 diff、可用 `llmtest` 零端点测试；不是配置文件里的隐式差异，更不是各自 fork 一份产品的 N 份分叉维护。

**机制单点，策略分布。** 审批挂起-续流与 fail-closed、沙箱不变量、网络容错、上下文经济——全系统一致的机制只有一份实现；写工具名单、ArgsForce、提示词、工具面、出口白名单——各系统的策略互不渗透。机制修复（尤其安全修复）升一个依赖版本即全系统落地，策略演进互不牵连。

**契约面即协作面。** 业务团队只见 `contract`（`Tool` / `Suspend` / 事件族），写工具、拼提示词不需要懂 agent 内部；基座团队守机制与安全不变量。边界由两侧守卫固化——业务仓的“0 import eino”测试与基座仓的依赖白名单——两个团队并行演进，接口不漂移。

**能力按需启用。** 新系统从最小装配（四项必填）起步，验证后再开沙箱、子代理、拓扑、动态工具装载。能力面不裁剪、装配面自由裁剪：既不存在“为了一个能力接受整套产品功能捆绑”，也不存在“这个场景用不上就从基座删掉”。

## 术语

多代理技术按双轴命名：**多代理编排**（现场编排，orchestrator-workers——父 agent 逐轮决定派谁）与**动态工作流**（agent 把编排写成脚本制品运行）是两种机制；**子代理**（spawn）是唯一原语，同步调用与后台派生（`background:true`，先返回 agentId、完成后再回传通知）是它的两种调用语义；并行/顺序/条件只是拓扑，不构成机制名。
