# 01 · 为什么是 eino

## agent 与业务系统的关系

模型能力跨过实用门槛后，每个业务系统都要回答：agent 与业务系统是什么关系。现有四种思路：

- **思路一：业务系统各自智能化。**每个系统内置自己的 agent，智能化是系统的内生能力——工具、权限、审批、会话都在系统自己的工程里。
- **思路二：一个全能 agent 操作所有系统。**业务暴露 API、插件或 MCP 工具，由一个足够完善的 agent 统一对接管理。这是当前的主流路径：业务提供接口，生态提供插件，用户安装技能。
- **思路三：agent 作为独立服务，业务系统调用。**agent 以服务、CLI 或 SDK 的形态独立存在，业务系统在流程节点上按需调用。
- **思路四：不做 agent，做 AI 功能点。**逐功能直调模型——摘要、填充、单轮问答；无循环、无工具面。

四种思路并不互斥——一个系统可以既有功能点内嵌（思路四），又在个别环节调用外部 agent 服务（思路三）。分野在于**长程、多步、带工具与审批的工作流由谁承载**。

**einox 取思路一。agent 的价值来自嵌入领域系统后获得的**数据（业务真源与工具面）、**权限**（门禁与审批流）与**流程**（工作流与人机协作节奏）：作为业务系统的内置组件，这三者是原生结构——审批卡出现在业务自己的界面，写入经过业务自己的门禁，会话归属于业务自己的用户；在通用对话界面中则都要外挂补齐。其余思路各有缺口：思路二能力归 agent，业务自有的工具、技能与安全边界无处安放；思路三隔着协议边界，类型契约止步于报文形状，审批回调与权限判定都是跨进程往返；思路四没有循环与工具面，承载不了工作流。

结论：智能化内建于业务系统，基座的形态是**可装配的库，不是应用**——交互形态（终端 / Web / IM / 语音）与业务面归应用，基座只提供机制。

## 五种架构路线

实现“业务系统各自智能化”，agent 能力要以某种架构到达业务系统。下文一条路线一节，节标题即其**形态**。前四条路线（应用、平台插件、SDK、配置驱动）指向同一个目标——**由他方提供的一个足够完善的 agent**：业务是消费者，自有的工具与边界分别靠 fork 二次开发、插件、协议客户端、配置声明往里补。第五条（装配）是 **agent 工厂**——基座不产出 agent，每个业务系统用它生产自己的那个。

思路一的目标场景中，业务有自己的工具、技能与安全边界要求，交互通道未必有界面（电话语音、实时流媒体），部署形态不定（个人独占与多租户共享皆有可能）。五条路线都能适配，差别在方法与成本。每节按三条轴对照——**架构**（业务能力以什么为载体、机制由谁养护）、**跨形态**（换交互通道或部署形态要动哪一层）、**agent 工厂**（第 N 个业务的边际成本是多少）；**交付**是第四条轴，只在要出两套制品的形态上成为成本。装配路线的代价（没有开箱即用，每个业务系统都要写组装根）与其余各节同样列出。

### 应用形态

典型开源产品：codex、Gemini CLI——都是 coding agent；通用域的同形态标杆（ChatGPT、Devin、Manus）均为闭源产品。开源代表集中在 coding 域不是偶然：应用形态的优点要完全兑现，依赖两个属于目标领域而非形态本身的前提——领域有公共接口，应用的通用工具层零适配即覆盖；应用的用户域就是真实用户本人。coding 域两者天然成立：接口是文件与命令，用户就是开发者，下述结构缺口在此不显形；业务系统两个前提皆无，缺口全部显形——开源产品在 coding 域的成功不反证这些缺口。

- **优点**：
  - **开箱即用**——安装即得完整 agent：工具面、会话、审批界面、权限模型都在一份制品里，零装配。
  - **业务零重构（止于暴露面）**——暴露 API（或执行其无界面 CLI）即获智能化，agent 以外挂方式到达，业务工程不动一行；前提是能力面止于 API 暴露面，超出部分见下。
  - **需求汇成一份能力**——全体用户的功能请求与真实使用压测同一份工具层、沙箱与权限模型，一次建成、全体受益、升级即时到达——成熟速度是单业务自建在同等投入下达不到的。
  - **交付最简**——业务侧只交付 API，agent 侧一个制品、包管理器分发；不产生其余三类形态的双制品、双节奏问题。
- **缺点**：结构缺口而非能力缺口——功能都能实现，成本落在三条轴上。
  - **架构**——能力归应用：agent 的能力面等于 API 暴露面与应用工具层封装的乘积，业务自有的工具与边界要起作用只能做进应用源码——推给上游（走应用的排期与取舍），或 fork 拆引擎自己养（人工合并，分叉随拖延期加深）；会话归应用的用户域、审批落在应用的界面，业务原生的工具面与领域门禁只能经 API 外挂。
  - **跨形态**——工件出厂即定型一种形态：codex 出厂是终端应用（后开的 app-server 是同一产品的第二条通道，见总表后的复合分析，不改出厂形态），要语音通道、多租户服务端或瘦客户端，要么等上游出该形态，要么动能力层自己分叉。
  - **agent 工厂**——产出单位是一个成品 agent，业务是消费者不是生产者：N 个业务的差异需求挤在同一 roadmap 上竞争排期、安全责任集中到应用；要各自的 agent，即回到 fork。

### 平台插件形态

典型开源产品：OpenClaw（个人助理网关，通道 + skills）、dsh（DeepSeek Harness，架构口号“一切皆插件”）——这条路线的开源代表明显更密：平台的护城河在生态规模，开源与形态激励相容（对照应用形态通用域标杆全闭源）。

- **优点**：三条轴上各向业务侧买回一步；个人助手场景是三者交汇——用户不写代码，长尾技能由市场聚合，形态与机制全由平台承担。
  - **架构**——载体从应用源码换成插件：业务能力是代码，经设计的缝进入（平台用什么语言，插件就用什么语言），定制不 fork；机制养护平台化——会话、审批、多租户由平台统一养，接受平台机制的业务零机制成本。
  - **跨形态**——形态工程平台化：平台已有的通道与形态对全部插件即时可用（OpenClaw 的一个 skill 即达其全部消息通道），业务不为形态写代码；平台每新增一种形态，存量插件全体受益。
  - **agent 工厂**——边际成本一个插件：第 N 个业务接入的成本是写一个插件而非 fork 平台，没有合并线；市场即分发，一个插件触达平台全部用户，生态正反馈；本体不膨胀——能力随生态增长，平台核心不变大。
- **缺点**：与应用形态同一个问题——功能都能实现，结构成本换了位置。
  - **架构**——载体从应用源码移进插件，业务侧有了承载之处，但缝在平台手里：钩子开在哪、权限给到什么粒度是平台的封闭枚举，想插的点平台没开，回到 fork；会话归属、审批通道、多租户划分等底层机制均由平台决定，业务只能接受平台的机制形状。
  - **跨形态**——分叉单位从应用上升到平台：插件改变不了平台的形态，换形态（语音通道、无界面、多租户）是平台的架构决策，业务在缝里无能为力。
  - **agent 工厂**——业务生产的是配件不是 agent：agent 本体（循环、机制、升级节奏）是平台单例，N 个业务共享其全部机制决策；插件生态的质量与维护参差构成供应链风险，且随接入的插件数累积。
  - **交付**——平台工件与插件两套制品、两套节奏，平台 API 破坏性版本即插件返工；本地平台之外还需在线插件库，离线场景只能软件包导入插件、预配置后交付，agent 与业务仍是两套界面。

### SDK 形态

典型开源产品：Agno（AgentOS 把 agent 起成 FastAPI 服务）、Letta（前 MemGPT，stateful agent 服务器）；coding 域的实例是 codex app-server、Gemini CLI 的 ACP 模式——协议面正被 MCP（工具层）与 ACP（客户端层）标准化。这些实现多为“库 + 服务运行时”对子：服务形态是自家库的组装，卖给用户的缝是协议面——业务代码进不了服务进程。

- **优点**：把 agent 部署成共享服务，业务经协议消费——服务端多租户场景是三条轴交汇：一份运行时划域服务 N 租户，客户端形态各自装配。
  - **架构**——协议面语言中立，业务侧任选语言；进程隔离——故障域与凭据域分离，业务凭据不必交给 agent 运行时；无界面场景天然适配（批处理节点、定时任务——交互本来就是报文）。
  - **跨形态**——前端形态自由：交互形态长在客户端侧，终端 / Web / IM / 无界面都是客户端的装配，换前端不动运行时。
  - **agent 工厂**——边际成本一份客户端胶水：N 个业务共享同一份运行时，比插件共享得更彻底（整条运行时）；多租户即把运行时部署为共享服务、按租户划域；机制由运行时方养，业务零机制成本。
- **缺点**：一切交互经由协议——功能都能实现，成本是边界两侧的永久对账。
  - **架构**——载体降格为协议报文：自定义工具、审批回调、权限判定都是跨进程往返；类型契约止步于报文形状，协议破坏运行期才暴露；会话与账号分属两个域，两侧要做映射与对账——业务审批界面成了运行时事件总线上的外挂订阅者。
  - **跨形态**——协议成为形态上限：事件推送、流式、挂起恢复都要协议承载，协议没覆盖的诉求（IM 长连接、实时语音流）要运行时配合改；协议演进权在运行时单方——MCP / ACP 标准化只是把“跟运行时节奏”变成“跟标准节奏”，推送关系没变。
  - **agent 工厂**——业务生产的是客户端不是 agent：循环、机制、模型策略是运行时单例；业务自定义能力要么经协议当数据投喂（工具定义、提示词以报文传），要么下沉进运行时进程（回到插件或 fork 的账）。
  - **交付**——两套制品、双升级节奏，运行时要独立部署与运维，版本偏差需要管理。

### 配置驱动形态

典型开源产品：Dify、Langflow——恰是两种亚型：编排平台与可视化构建器；n8n 同形态但为 fair-code 许可（非 OSI），不计入开源之列。集中在提示词与流程编排场景（RAG、客服、内部工作流），coding 域几乎缺席——方言表达力止于流程与提示词，覆盖不了工具面密集的场景。

- **优点**：起步最快——修改配置即可运行。
  - **架构**——载体是配置数据：提示词、工具挂接、流程编排以方言声明，非工程师可读可改；配置可 diff、可回滚，执行语义归运行时。
  - **跨形态**——运行时内置的形态集合（Web 应用、API 端点、嵌入组件）开箱即得：配置一次，多通道生效。
  - **agent 工厂**——边际成本一份配置，且业务人员可生产——五条路线里门槛最低的一条。
- **缺点**：表达力止于配置语法——功能都能实现，复杂度不会消失，只会转移。
  - **架构**——超出方言的策略（审批矩阵、领域门禁、多租户）退化为旁挂脚本，脱离类型系统与测试的保障，方言与脚本双载体；安全边界只有开关粒度、没有策略粒度；配置错误运行期才暴露——静默漂移，排障时间不可预期。
  - **跨形态**——形态集合是运行时的枚举，配置改变不了运行时；方言是运行时私有的，换运行时即配置重写——锁定由此而生。
  - **agent 工厂**——产出的是配置不是 agent；复杂场景的成本转移为配置膨胀、旁挂脚本、改运行时源码（回到 fork）；业务能力是数据不是代码，游离在业务工程体系（测试、review、同一制品）之外。
  - **交付**——仍是独立运行时，交付两套；典型运行时是容器化全家桶（Dify 一套 docker-compose 十余容器），与受限网络环境的单二进制诉求相悖。

### 装配形态

典型开源产品：LangChain，以及 einox 的地基 eino 本身（Go 列；配置驱动的 Coze Studio 也以 eino 为地基）。“agent 能力以库到达业务代码”本就是主流路线，主场在业务系统嵌入场景（coding 域被应用形态占据）。各家覆盖的机制谱系与缝的形态各异；einox 在 eino 之上的声明点是机制完整（审批包装、沙箱、会话域、guard）且缝封闭于编译期枚举。

四个事实界定这一形态：`contract/` 是唯一端口面（零 eino 类型——依赖倒置隔离地基，更换地基业务零感知）；全部能力经 `engine.Options` 组装根注入、构造期定型（运行面控制反转：引擎驱动循环、事件回调扇出），无容器、无运行时注册表；机制归基座并守安全不变量，策略经装配注入；`Options` 字段即全部装配缝——封闭枚举、编译期可见，新缝走基座演进，不经旁挂。

- **优点**：本体的倒置——业务代码为体、机制为客，三条轴上是同一件事的三个面。
  - **架构**——业务能力的载体是业务代码：工具、审批名单、提示词、边界策略是业务工程的一等代码，可测试（`llmtest` 零端点）、可 review、随业务系统同一制品交付；机制（审批包装、错误回喂、摘要、沙箱）由基座在装配链统一施加，业务不重写机制。
  - **跨形态**——形态中立，跨形态不分叉：基座不带 UI 与传输假设，交互通道（终端 / Web / IM / 语音 / 无界面执行）与部署形态（独占单二进制 / 多租户单进程划域）都是装配决策——同一套基座与业务代码在不同形态各自装配，形态之间只是组装根差异。对照其余四条：应用与配置驱动的工件可运行、形态随工件出厂，平台插件的形态是平台的架构决策，三者换形态都要动能力层，一个形态一条分叉；SDK 不分叉，但形态上限是协议（见上节）——形态自由与形态不分叉是两件事，装配形态两者兼有。
  - **agent 工厂**——产出单位是业务各自的 agent，不是那个“足够完善”的 agent：基座是生产资料（机制层），组装根是生产线，第 N 个业务的边际成本是一个组装根；每个产出的 agent 原生继承全部机制与安全不变量——N 个 agent，零分叉。
- **缺点**：代价在开工时一次列出——此后每多一个业务只付一个组装根的边际成本。
  - **agent 工厂**——没有开箱即用：每个业务系统要写组装根，产线要业务自己开。
  - **架构**——扩展缝封闭于 `Options` 枚举：三方插件、运行时增删不在设计目标内——对照插件形态，开放换生态、付供应链与碎片化，封闭换编译期可枚举、付生态缺位。
  - **跨形态**——形态自由不是免费：每个形态各写一个组装根，传输层（API、推送、多实例扩展）归应用自建。

### 总表

| 形态     | 业务能力的载体         | 能力复用通道             | 变更到达业务侧                       | 交付               |
| ------ | --------------- | ------------------ | ----------------------------- | ---------------- |
| 应用     | API 面（超出则进应用源码）  | 应用工件 + API 面（超出则 fork） | 推送：应用升级即时到达；分叉部分人工合并，随拖延期加深 | 一套（agent 是应用方的制品）   |
| 平台插件   | 插件（缝由平台枚举）       | 平台工件 + 插件缝          | 推送：破坏性版本 = 插件返工，节奏由平台定       | 两套（平台 + 插件）       |
| SDK    | 协议报文（或下沉进运行时进程）  | 运行时工件 + 协议面         | 跟运行时节奏，协议破坏运行期才暴露           | 两套（业务 + 运行时）      |
| 配置驱动   | 配置 / 脚本         | 运行时工件 + 配置方言        | 静默漂移，排障时间不可预期               | 两套（业务 + 运行时）      |
| **装配** | **业务代码**        | **库工件 + 类型化装配点**     | **拉取：升依赖才进入，破坏点编译期可枚举**     | **一套（编进业务系统制品）**   |

表是理想型，真实产品常复合。分析法是按通道拆解、逐行对照：出厂工件一行、能力复用通道一行、地基库用法一行，各自查行。Pi 是典型：出厂是可运行 CLI（应用行）；能力复用的主通道是扩展 API——宿主定义接口、运行时加载的 TypeScript 模块（插件行）；地基包 pi-ai / pi-agent-core 可脱离 CLI 独立消费，在业务自己的进程与制品里组 agent（装配行——构建原语库用法）——横跨三行，独缺 SDK 行：没有独立部署的运行时工件，也没有对外协议面。Agno 横跨两行：AgentOS 把 agent 起成 FastAPI 服务、对业务是协议面（SDK 行），Agno 自身的库则在业务进程里组 agent（装配行）。复合不模糊分野：“业务能力的载体”一列对每条通道都单值；装配行内部的分野在站位不在行——Pi 的库是构建原语（统一 LLM API、会话与循环，不带权限与沙箱系统），einox 的声明点是机制基座加封闭缝。codex 的 app-server、opencode 的 serve 与插件缝同理：在前四行内复合，仍在前四行。

最后一行即全部代价与收益：一个组装根换能力复用、变更可控与单制品交付（裁剪见 [04-assembly.md](04-assembly.md)）。装配路线为何能拆开“能力 | 成品”，见 [02-why-einox.md](02-why-einox.md)；第三方实现的移植与借鉴（apply_patch 格式、沙箱策略等）在 [NOTICE](../NOTICE.md) 逐项署名。

## 交付形态

交付形态取决于部署环境的网络条件：

- **联网环境**（面向互联网用户的产品）：网络不受限，npm、pip、brew 等包管理器与在线分发渠道可用，运行时依赖不构成交付负担；
- **受限网络环境**（内网、离线部署）：网络策略约束下载与更新，交付越简单越好——静态编译的**单二进制**是最简形态：一个文件，部署即拷贝、升级即替换，前端资源可嵌入二进制内，无需解释器、运行时或旁挂服务。

einox 面向的场景以受限网络环境为主，交付形态据此收敛到编译型语言：

| 语言         | 代表框架                                                 | 交付形态                    |
| ---------- | ---------------------------------------------------- | ----------------------- |
| Python     | LangChain/LangGraph、OpenAI Agents SDK、AutoGen、CrewAI | 解释器 + 依赖环境              |
| TypeScript | Vercel AI SDK、LangChain.js、Mastra                    | Node 运行时 + node_modules |
| Rust       | Rig                                                  | 编译型，静态单二进制              |
| Go         | eino、langchaingo                                     | 编译型，静态单二进制              |

Go 与 Rust 在交付维度等价，进一步取舍见下一章。

## 为什么是 eino

选型条件：框架以库形态提供完整的 agent 共性底层（消息 schema、模型组件抽象、编排原语、agent 内核）；编译型语言，支持单二进制交付；不改源码消费、随上游升级。

eino 满足全部条件：消息 schema、模型组件抽象（anthropic / openai 协议组件）、compose 编排原语、adk agent 内核与模型重试协议、eino-ext 组件生态（MCP、搜索等），且全部以库形态提供。Go 的工程特性与嵌入场景适配：goroutine 并发模型承载多会话、多 agent、多子代理并发，静态类型提供进程内契约。模型接入的底层工作（协议适配、流式、重试）由 eino 承担，einox 在其上只补运行时关切。

为什么在 eino 与业务 agent 之间还需要一层 einox，见 [02-why-einox.md](02-why-einox.md)。
