# 01 · 为什么是 eino

## agent 与业务系统的关系

模型能力跨过实用门槛后，每个业务系统都要回答：agent 与业务系统是什么关系。现有四种思路：

- **思路一：业务系统各自智能化。**每个系统内置自己的 agent，智能化是系统的内生能力——工具、权限、审批、会话都在系统自己的工程里。
- **思路二：一个全能 agent 操作所有系统。**业务暴露 API、插件或 MCP 工具，由一个足够完善的 agent 统一对接管理。这是当前的主流路径：业务提供接口，生态提供插件，用户安装技能。
- **思路三：agent 作为独立服务，业务系统调用。**agent 以服务、CLI 或 SDK 的形态独立存在，业务系统在流程节点上按需调用。
- **思路四：不做 agent，做 AI 功能点。**逐功能直调模型——摘要、填充、单轮问答；无循环、无工具面。

四种思路并不互斥——一个系统可以既有功能点内嵌（思路四），又在个别环节调用外部 agent 服务（思路三）。分野在于**长程、多步、带工具与审批的工作流由谁承载**。

**einox 取思路一。**agent 的价值来自嵌入领域系统后获得的**数据**（业务真源与工具面）、**权限**（门禁与审批流）与**流程**（工作流与人机协作节奏）：作为业务系统的内置组件，这三者是原生结构——审批卡出现在业务自己的界面，写入经过业务自己的门禁，会话归属于业务自己的用户；在通用对话界面中则都要外挂补齐。其余思路各有缺口：思路二能力归 agent，业务自有的工具、技能与安全边界无处安放；思路三隔着协议边界，类型契约止步于报文形状，审批回调与权限判定都是跨进程往返；思路四没有循环与工具面，承载不了工作流。

结论：智能化内建于业务系统，基座的形态是**可装配的库，不是应用**——交互形态（终端 / Web / IM / 语音）与业务面归应用，基座只提供机制。

## 五种架构路线

实现「业务系统各自智能化」，agent 能力要以某种架构到达业务系统。前四条路线（应用、平台插件、SDK、配置运行时）都以**一个足够完善的 agent** 为目标：靠二次开发补齐功能、插件、配置、技能，得到最终成品。与思路一相配的形态是 **agent 工厂**——基座不产出 agent，每个业务系统用它生产自己的那个。

思路一的目标场景中，业务有自己的工具、技能与安全边界要求，交互通道未必有界面（电话语音、实时流媒体），部署形态不定（个人独占与多租户共享皆有可能）。五条路线都能适配，差别在方法与成本；einox 自身的代价（没有开箱即用，每个业务系统都要写组装根）一并列出。

### 应用形态

- **优点**：开箱即用；业务零重构——暴露 API（或执行其无界面 CLI）即获智能化。
- **缺点**：能力归应用。agent 对业务能做什么，等于 API 暴露面与应用工具层封装的乘积——业务自有的工具、技能与安全边界没有安放之处，只能做进应用。这是结构缺口而非能力缺口：应用与模型再强，也替代不了业务原生的工具面与领域门禁；而把每个业务的需求都做进应用，应用必然随业务数膨胀——能力中心成为排期瓶颈、替所有业务承担安全责任；会话归应用的用户域，审批落在应用的界面。

### 平台插件形态

- **优点**：业务侧有承载之处——平台用什么语言，插件就用什么语言，语言不是这条路线的障碍；个人助手场景的最优解：通用对话界面 + 技能市场，按需安装插件，本体不膨胀。
- **缺点**：与应用形态同一个问题——对业务的支持方式。插件开发到最后仍是一个应用支撑多种业务，膨胀转移进插件生态，每接入一种业务就多一个插件；会话归属、审批通道、多租户划分等底层机制均由平台决定；部署负担重——本地 agent 之外还需在线插件库，离线场景只能以软件包导入插件、预配置后交付，agent 与业务仍是两套制品、两套界面。

### SDK 形态

- **优点**：无界面场景天然适配；多租户即把运行时部署为共享服务；进程隔离。
- **缺点**：一切交互经由协议——自定义工具、审批回调、权限判定都是跨进程往返，类型契约止步于报文形状；会话与账号分属两个域，两侧要做映射与对账；双制品、双升级节奏，版本偏差需要管理。

### 配置驱动形态

- **优点**：起步最快——修改配置即可运行。
- **缺点**：表达力止于配置语法——必须写代码的策略（审批矩阵、领域门禁、多租户）超出配置表达力时，退化为旁挂脚本，脱离类型系统与测试的保障；安全边界只有开关粒度、没有策略粒度；仍是独立运行时，交付两套。

### 装配形态（einox）

四个事实界定这一形态：`contract/` 是唯一端口面（零 eino 类型——依赖倒置隔离地基，更换地基业务零感知）；全部能力经 `engine.Options` 组装根注入、构造期定型（运行面控制反转：引擎驱动循环、事件回调扇出），无容器、无运行时注册表；机制归基座并守安全不变量，策略经装配注入；`Options` 字段即全部装配缝——封闭枚举、编译期可见，新缝走基座演进，不经旁挂。

- **优点**：业务能力的载体是业务代码——工具、审批名单、提示词、边界策略是业务工程的一等代码，可测试（`llmtest` 零端点）、可 review、随业务系统同一制品交付；形态中立——无 UI 假设、事件传输无关（语音网关、流媒体管线即前端），部署形态（个人独占 = 单二进制 / 多租户 = 单进程按 Owner/SID 划域）是装配决策而非架构分叉；机制（审批包装、错误回喂、摘要、沙箱）由基座在装配链统一施加，业务不重写机制。
- **缺点**：没有开箱即用，每个业务系统要写组装根；扩展缝封闭于 `Options` 枚举——三方插件、运行时增删不在设计目标内。

### 总表

| 形态 | 业务能力的载体 | 能力复用方式 | 变更到达业务侧 | 交付 |
|---|---|---|---|---|
| 应用 | API 面 | fork 源码拆引擎 | 人工合并，分叉随拖延期加深 | 应用方的一个 agent |
| 平台插件 | 插件 | 平台工件 + 插件缝 | 推送：破坏性版本 = 插件返工，节奏由平台定 | 两套（平台 + 插件） |
| SDK | 协议报文 | 运行时工件 + 协议面 | 跟运行时节奏，协议破坏运行期才暴露 | 两套（业务 + 运行时） |
| 配置驱动 | 配置 / 脚本 | 运行时工件 + 配置方言 | 静默漂移，排障时间不可预期 | 两套 |
| **装配（einox）** | **业务代码** | **库工件 + 类型化装配点** | **拉取：升依赖才进入，破坏点编译期可枚举** | **一套（agent 编在业务系统里）** |

最后一行即全部代价与收益：一个组装根换能力复用、变更可控与单制品交付（裁剪见 [04-assembly.md](04-assembly.md)）。装配路线为何能拆开“能力 | 成品”，见 [02-why-einox.md](02-why-einox.md)；第三方实现的移植与借鉴（apply_patch 格式、沙箱策略等）在 [NOTICE](../NOTICE.md) 逐项署名。

### 跨形态

部署形态不定不只是范围声明——它摆出一条隐性约束：**换形态时，各路线各自要动什么**。目标形态会随业务演进：个人独占的工具是单二进制，组织共享是服务端多用户；两者的合流是当前主流服务端 agent 产品的部署选择——**执行在服务端，手机 app 当瘦客户端**：沙箱与模型密钥不出服务端，手机只发起、渲染事件流、接收推送；执行不受客户端生命周期约束（退后台、锁屏、换设备不中断）。五条路线都能到达这一形态，差别照旧在方法与成本：

- 前四条路线的工件可运行、形态随工件出厂——应用带界面、平台带宿主与生态、SDK 带协议与进程边界、配置带 schema；形态在能力侧，成品就继承它，换形态即改能力层（推动上游或 fork）。
- 装配形态的工件不可运行、形态由组装根赋予——CLI 单二进制与多租户服务端进程是同一份基座的两个组装根；业务代码（工具、审批名单、提示词、边界策略）跨形态原样复用，不因形态重写。

## 交付形态

交付形态取决于部署环境的网络条件：

- **联网环境**（面向互联网用户的产品）：网络不受限，npm、pip、brew 等包管理器与在线分发渠道可用，运行时依赖不构成交付负担；
- **受限网络环境**（内网、离线部署）：网络策略约束下载与更新，交付越简单越好——静态编译的**单二进制**是最简形态：一个文件，部署即拷贝、升级即替换，前端资源可嵌入二进制内，无需解释器、运行时或旁挂服务。

einox 面向的场景以受限网络环境为主，交付形态据此收敛到编译型语言：

| 语言         | 代表框架                                                 | 交付形态                    |
| ---------- | ---------------------------------------------------- | ----------------------- |
| Python     | LangChain/LangGraph、OpenAI Agents SDK、AutoGen、CrewAI | 解释器 + 依赖环境              |
| TypeScript | Vercel AI SDK、LangChain.js、Mastra                    | Node 运行时 + node_modules |
| Rust       | Rig                                                  | 编译型，静态单二进制              |
| Go         | eino、langchaingo                                     | 编译型，静态单二进制              |

Go 与 Rust 在交付维度等价，进一步取舍见下一章。

## 为什么是 eino

选型条件：框架以库形态提供完整的 agent 共性底层（消息 schema、模型组件抽象、编排原语、agent 内核）；编译型语言，支持单二进制交付；不改源码消费、随上游升级。

eino 满足全部条件：消息 schema、模型组件抽象（anthropic / openai 协议组件）、compose 编排原语、adk agent 内核与模型重试协议、eino-ext 组件生态（MCP、搜索等），且全部以库形态提供。Go 的工程特性与嵌入场景适配：goroutine 并发模型承载多会话、多 agent、多子代理并发，静态类型提供进程内契约。模型接入的底层工作（协议适配、流式、重试）由 eino 承担，einox 在其上只补运行时关切。

为什么在 eino 与业务 agent 之间还需要一层 einox，见 [02-why-einox.md](02-why-einox.md)。
