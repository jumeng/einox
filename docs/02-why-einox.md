# 02 · 为什么需要 einox：基座的设计与分层

> 本文回答：为什么 eino 与业务 agent 之间还需要一层基座（“设计原则”）、这层基座为什么必须是库（“形态判定”）、三层栈如何划分（“各层是什么”）、一份基座如何服务多套业务系统（“场景适配”）。

## 设计原则

先回答必要性。eino 解决的是“怎么调模型、怎么组装组件”；生产可用的 agent 系统还需要一整层“怎么跑起来”的运行时关切，它们不在 eino 的能力面里：

1. **会话生命周期**——会话归属、快照、续聊、排队消息、运行中改向（steering）、TTL 清理；
2. **HITL 审批**——写操作挂起等人批准、恢复续流、参数级强制审批（任何模式不豁免）、fail-closed；
3. **执行安全**——命令沙箱（Landlock/seccomp/restricted token/Seatbelt）、网络出口治理、代码仓 worktree 挂载与“不 push”边界；
4. **网络容错**——流式空闲哨兵、错误分类（致命停机/可重试）、有界重连——缺少它们，一条静默失效的连接会让会话永远停留在 running 状态；
5. **harness**——出站上下文经济（超长工具结果外置换指针、历史超窗清除）、长会话摘要、子代理隔离与编排、动态工具装载；
6. **通用工具族**——apply_patch / 文件 / 命令执行 / 网页提取等，每个 agent 系统都需要。

直接在 eino 上构建业务，这六项会散落在每个业务系统中重复实现，且互相不可复用。einox 的职责是将它们收敛为**机制**，一次实现、处处装配；基座自身的设计遵循五条原则：

- **机制归基座，内容归业务**：审批的挂起/续流是机制，审批名单是内容；skill 的发现与注入是机制，skill 本身是内容。
- **应用对基座只装配、不修改**：全部能力经 `engine.Options` 注入与启停，基座源码不改一行。
- **业务 0 import eino**：eino 依赖只存在于本仓；业务只见 `contract` 契约面（零 eino 类型）——更换地基只影响基座内部。
- **能力面不裁剪，装配面自由裁剪**：多代理编排、动态工作流、harness 等是基座必备机制，不因某个应用暂不使用而删除；应用不装配即不生效。
- **实现序**：优先复用 eino 既有能力（中间件/原语/预置拓扑），确无对应能力才自研，并在设计文档记录依据。

## 形态判定：拆“能力 | 成品”，不只是“能力 | 内容”

五条原则回答了基座怎么设计；本章进一步回答它为什么必须是**库**——“能力 | 成品”的拆分唯有库形态能完成，且拆分本身对基座是一项纪律。这也是 [01](01-why-eino.md) 架构比较选定装配形态的深层依据。

这一层的核心价值是把**能力补全**与**最终成品**拆开，让能力补全一次完成、N 处复用。拆分成立要求能力工件满足三个条件：**可复用**（N 处消费不分叉）、**业务差异装配得出**（不必改能力层源码）、**形态中立**（不携带产品形态，否则 N 个成品形态趋同）。三个条件对各路线都不是能否做到的问题——应用形态靠 fork 也拆得出引擎——真正的差别在方式，以及两项按工作量与时间结算的成本：**对齐成本**（能力层如何持续跟上上游）与**传导成本**（变更到达业务侧后，业务跟进的工作量是否可预期）。

差别源于能力工件的形状：**可运行之物必带形态**——应用带界面、平台带宿主与生态、SDK 带协议与进程边界、配置带 schema。形态在能力侧，成品就继承它；要改形态就得动能力层，而动能力层只有推动上游或 fork 两条路，付出的都是排期与人力。库的能力工件是**不可运行的代码**，形态由装配赋予——业务差异不动能力层即可表达，对齐收敛为依赖升级，破坏点编译期可枚举，变更以拉取方式到达。**其余四条路线拆的是“能力 | 内容”，装配路线拆的是“能力 | 成品”——成品包含形态与交付，唯有库形态能完成这一拆分。**

两个退化情形同理：fork 是以修改代替装配，能力补全实际被做了 N 次；平台的机制包当库用可行，但其零件为平台而非嵌入塑形，也不被对方的设计守护——可行不等于被设计支持，可行不等于成本可预期。

判定同时是对基座自身的纪律：契约面零形态与 nil 纪律守护复用面——每混进一个形态假设，就损失一块复用面；装配点的表达力与契约的稳定守护业务的跟进成本——业务差异若只能改基座源码表达，分离即告失败；`contract` 面的破坏性变更就是业务工作量的上界：窄、少动、编译期可检。

## 各层是什么

设计原则与形态判定至此合流：eino 之上、业务 agent 之下，需要一层库形态的基座——三层栈的职责划分如下：

| 层 | 角色 | 提供 | 不提供 |
|---|---|---|---|
| [cloudwego/eino](https://github.com/cloudwego/eino) | LLM 应用框架（地基） | 模型组件抽象、消息 schema、编排原语（compose）、agent 内核（adk）、官方组件生态（eino-ext） | agent 运行时关切：会话生命周期、审批挂起、沙箱执行、网络容错、上下文整形 |
| **einox** | 通用 agent 基座（本仓） | 循环引擎、会话域、HITL 审批、harness（上下文整形/摘要/子代理隔离/动态工具装载）、沙箱、网络容错、通用工具族、skill 机制、检查点 | 业务内容：业务工具、提示词内容、审批名单、UI、数据门禁 |
| 业务 agent | 应用（不在本仓） | 按上述机制装配出自己的 agent 系统 | ——机制由基座承担 |

再从开发节奏看这条栈：einox 是对 eino 的**二次开发**，产物刻意止步于**半成品**；业务系统的组装根装配是**三次开发**，产物才是成品——各自的 agent。其他架构的二次开发通常以成品收尾，einox 把完成度边界划在“适配路径走通”——成品永远在业务侧诞生（拆分判定见上一章）。

## 场景适配：一份基座，多套业务系统

单系统嵌入时，库形态的价值是“不带产品外壳”；到组织级场景，这一价值才完整显形——这也是“agent 工厂”所指的场景：**一个团队为多套业务系统提供 agent 能力**，CRM、工单、数据平台、内部工具，每套都有自己的数据域、权限模型、审批流与交互形态。einox 为此提供的适配结构：

**同一份基座，N 个组装根。** 每个业务系统一个组装根——`engine.Options` 即该系统的 agent 定义。系统间差异是应用代码差异：可 review、可 diff、可用 `llmtest` 零端点测试；不是配置文件里的隐式差异，也不是各自 fork 产品的分叉维护。

**机制单点，策略分布。** 审批挂起-续流与 fail-closed、沙箱不变量、网络容错、上下文经济——全系统一致的机制只有一份实现；写工具名单、ArgsForce、提示词、工具面、出口白名单——各系统的策略互不渗透。机制修复（尤其安全修复）升一个依赖版本即全系统落地，策略演进互不牵连。

**契约面即协作面。** 业务团队只见 `contract`（`Tool` / `Suspend` / 事件族），写工具、拼提示词不需要了解 agent 内部；基座团队守机制与安全不变量。边界由两侧守卫固化——业务仓的“0 import eino”测试与基座仓的依赖白名单——两个团队并行演进，接口不漂移。

**能力按需启用。** 新系统从最小装配（四项必填）起步，验证后再开沙箱、子代理、拓扑、动态工具装载。能力面不裁剪、装配面自由裁剪：既不存在“为了一个能力接受整套产品功能捆绑”，也不存在“这个场景用不上就从基座删掉”。
